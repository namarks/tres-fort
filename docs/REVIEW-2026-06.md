# Très Fort — Holistic Review (June 2026)

Triggered by a real post-workout debrief: four concrete issues hit during a
session, used as the entry point for a deeper look at how the app holds up as a
gym executor. This doc records the diagnosis, what changed in this PR, and the
broader observations worth acting on next.

---

## 1. What's working (and shouldn't change)

The core architecture is sound and the right shape for a single-athlete,
AI-coached system:

- **One Worker, one service layer, two clients.** All D1 access funnels through
  `src/db.ts`; REST routes and MCP tools are thin wrappers. The editing
  endpoints added here cost ~30 lines precisely because the logic
  (`updateExercise`, `deleteTemplateExercise`) already existed and was sound —
  the only gap was that it was reachable from Claude but not from the app.
- **Two data classes, two consistency strategies.** Versioned plan tree +
  append-only logs is the right call and made the warm-up + slot-linking changes
  safe: set logs reference `exercise_id` / `template_exercise_id`, never
  positional indices, so editing the plan mid-workout can't corrupt logged work.
- **Audit + notes on every write.** Extending it to app-side edits (`actor='ios'`)
  was a one-liner per endpoint and keeps the trust/undo trail complete.

The thing to preserve: **Claude is the brain, the app is the executor.** The
fixes here deliberately do *not* move planning/analysis into the app. They let
you tweak the session in front of you (add a thing, drop a thing, warm up) — the
mechanical executor's job — while programming, periodization, and review stay
with Claude.

## 2. The four issues

### #1 — No in-app workout editing → **fixed (backend tested; iOS pending device verify)**

**Was:** the only way to add or remove an exercise was to talk to Claude. The
iOS app was read-only for plan structure; the backend already had
`updateExercise` / `deleteTemplateExercise` but only the MCP surface called them,
and REST exposed only add (`POST /api/days/:id/exercises`) + day rename.

**Now:**
- New REST endpoints — `PATCH /api/days/:dayId/exercises/:teId` (edit targets /
  rest / warm-up / order) and `DELETE /api/days/:dayId/exercises/:teId` (remove,
  detaching historical sets) — thin wrappers over the existing db functions,
  version-bumped and audited as `actor='ios'`.
- iOS: an **Edit workout** sheet (from the Today screen and the runner overflow
  menu) with add / remove / reorder, backed by new `APIClient` methods.

**Design decision worth knowing:** in-app edits mutate the **day template** (the
versioned plan), not a per-session override. There is no session-scoped exercise
list in the data model, and editing the template is exactly how Claude edits, so
this keeps one source of truth. The consequence: an added erg warm-up *recurs* on
that day. For a warm-up that's usually what you want; for a true one-off ("just
today, add a thing"), you currently remove it afterward. A genuine per-session
override is a real future option (see §3).

### #2 — No warm-up support (couldn't add an erg warm-up) → **fixed**

**Was:** `is_warmup` existed only on *logged sets*, never on a *plan slot*, so a
warm-up couldn't be prescribed — and there was **no ergometer/cardio exercise in
the catalog at all** (the only "cardio" string in the repo was a comment). An erg
warm-up was literally unrepresentable.

**Now (migration 0026):**
- `template_exercises.is_warmup` — a slot can be a prescribed warm-up. Its logged
  sets default to `is_warmup=1` (the backend infers this from the slot, so any
  client gets it right) and stay out of working-set rollups / session RPE.
- 8 cardio/erg catalog rows (rowing/bike/ski erg, treadmill, elliptical,
  StairMaster, stationary bike, jump rope), `modality='cardio'`, resolvable by
  alias ("erg", "rower", "echo bike", …).
- Cardio/erg slots reuse the existing **timed runner**: set `target_duration_s`
  and the app counts the effort down and logs the duration — a 5-min row is a
  first-class slot, not a hack. Claude can prescribe warm-ups too (`add_exercise`
  / `update_exercise` gained `is_warmup`).

### #3 — Exercises "crossed out" when logging out of order → **fixed**

Two distinct root causes, both addressed:

1. **Completion keyed on `exercise_id`, not the plan slot.** `isComplete` counted
   live sets for an `exercise_id` against `target_sets`. The same movement in two
   slots cross-attributed completion (finish one → both show green/done), and the
   iOS logger never sent `template_exercise_id` even though the column existed.
   *Fix:* iOS now sends `template_exercise_id`; completion, the set index, and the
   "completed sets" chips all key on the **slot** (`todaySlotSets`), with a
   fallback to `exercise_id` for sets logged by Claude/MCP. Same movement twice no
   longer mis-completes.

2. **The only forward navigation was "SKIP →".** To reach a later exercise you had
   to skip, which struck it through *and* dropped it from the queue
   (`nextIncompleteIndex` excludes skipped). Stepping ahead out of order to come
   back = permanent strikethrough. *Fix:* the bottom-right button is now a
   non-destructive **NEXT →**; an explicit, lower-emphasis "Skip this exercise"
   remains for genuinely dropping one. Moving around no longer marks anything
   skipped.

### #4 — No audio cue when rest ends → **added (iOS)**

The rest countdown was visual-only — useless with the phone pocketed and
headphones in. Added `RestCue`: at the moment rest elapses, a short chime + a
success haptic + a spoken "Rest's up — up next, &lt;exercise&gt;". Uses the
`.playback` audio category so it sounds through headphones and ignores the mute
switch, and `.duckOthers` so music/podcasts dip rather than stop. Fired by a
poll-to-deadline task on the model (robust to a suspended sleep, the same
lesson the timed-set runner learned), rescheduled on +15/−15 and cancelled on
DONE. Gated by a default-on `@AppStorage` flag so it can be silenced.

## 3. Deeper observations & recommended follow-ups

Beyond the four issues, things this review surfaced:

1. **`exercise_id` vs `template_exercise_id` coupling (medium).** This PR fixes
   the runner, but other places still group by `exercise_id` (history, volume,
   `lastWorkingSet`). That's *correct* for history (it's about the movement, not
   the slot), so no change — but worth a deliberate note: **slot identity for
   "today's execution," movement identity for "trends."** Keep that line clean.

2. **Per-session override vs template edit (medium).** The honest answer to "let
   me tweak *just today*" is a session-scoped exercise list (an
   `session_exercises` overlay, or a per-session `meta` patch the runner reads
   before falling back to the template). It's a real feature, not a bug, but it's
   the principled home for one-offs and would stop one-off tweaks from polluting
   the recurring plan. Deferred deliberately — the template edit covers the
   common case today.

3. **Cardio is duration-only (low).** The erg rows log time, not distance/
   calories/watts. Fine for warm-ups. If ergs become *conditioning* (not just
   warm-ups), they'll want a distance/cal field — at which point they overlap
   with the intervals.icu activity model and should probably route there, not
   into `set_logs`.

4. **`update_plan` full-rebuild now preserves `is_warmup`** (threaded through
   `ExerciseInput`), but it's worth a regression test that a full rebuild round-
   trips the flag, since the rebuild path is the one most likely to silently drop
   a new column in the future.

5. **iOS has no automated test gate.** The backend has 376 tests; the app has
   none, so every iOS change (including this one) rides on review + TestFlight.
   The completion/skip logic that caused #3 is exactly the kind of pure function
   (`todaySlotSets`, `nextIncompleteIndex`, the projection) that would benefit
   from a small XCTest target — high value, low effort, no UI harness needed.

6. **Audio-cue preference has no UI yet.** It's wired to an `@AppStorage` key
   (`restAudioCuesEnabled`, default on); a one-line toggle in the Profile tab
   would make it discoverable. Left out to keep this PR's surface tight.

## 4. Verification status

- **Backend:** fully covered. `test/edit_workout.test.ts` exercises add/edit/
  delete/reorder, the warm-up flag end-to-end, audit rows, set detaching on
  delete, and slot-inherited `is_warmup` on logged sets. Full suite green (376
  tests; catalog count assertions updated 246 → 254).
- **iOS:** written against existing patterns but **not compiled here** (no Xcode
  in this environment). Needs `cd ios && xcodegen generate` (to pick up the two
  new files) and a device/TestFlight pass — the established loop. The new files
  are `RestCue.swift` and `EditWorkoutSheet.swift`; everything else extends
  existing files.
